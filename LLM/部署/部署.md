## KV Cache 为什么会影响显存、并发和长上下文服务？

### 参考回答（已本地化）

保存历史 Token 的 K/V 需要额外显存，且 KV Cache 的规模会随上下文长度和并发请求数增加。

> **KV Cache 显存占用 ∝ 并发序列数 × 上下文长度**

因此，除模型权重外，**KV Cache 往往也是决定显存占用、最大并发量和长上下文服务能力的重要因素。**

原理与区别：[[LLM#KV Cache 是什么，为什么能加速逐 Token 生成？|KV Cache 是什么，为什么能加速逐 Token 生成？]]；[[对比问题#KV Cache 与 Prompt Cache 有什么区别？|KV Cache 与 Prompt Cache 有什么区别？]]。

## 不同 Agent 之间能否共享 KV Cache？

### 参考回答

**可以，但前提不是“它们属于同一个多 Agent 系统”，而是底层推理服务支持跨请求复用相同前缀对应的 KV 状态。Agent 身份本身通常不是决定条件。**

普通自回归推理中，每条正在生成的 Sequence 都会维护自己的 KV Cache。若两个 Agent 发起的是彼此独立的模型请求，这些 KV Cache 默认可以完全独立存在；只有当 Serving 层实现了 Prefix Caching / Automatic Prefix Caching 一类机制时，后来的请求才可能直接引用此前请求已经计算出的前缀 KV。

例如两个请求对应的 Token 序列分别是：

- Agent A：$[a,b,c,d,X,\ldots]$
- Agent B：$[a,b,c,d,Y,\ldots]$

如果底层支持前缀 KV 复用，那么 $a,b,c,d$ 对应的 KV 状态可以共享；从 $X$ 与 $Y$ 开始计算历史发生分叉，此后的 KV 状态也随之分叉。

这里必须强调“**相同前缀**”，而不是“文本里出现过相同片段”。某个位置的 K/V 不只取决于当前 Token，还取决于此前上下文、所在位置以及模型参数。于是：

- 同样的子串出现在不同历史之后，通常不能直接复用同一组 KV；
- 同样的 Token 出现在不同位置，也不能简单视作同一状态；
- 模型权重、LoRA / Adapter 或其他会改变前向计算结果的配置不同，也不能直接共享；
- 即使计算前缀相同，Serving 层的租户隔离、Cache Salt 或其他缓存作用域规则仍可能禁止跨请求共享。

因此更准确的条件是：

$$
\text{相同且兼容的模型状态}
+
\text{相同 Token 前缀}
+
\text{相同位置关系}
+
\text{允许共享的缓存作用域}
\Rightarrow
\text{前缀 KV 可复用}
$$

vLLM 的 Automatic Prefix Caching 就是一个直接例子：它缓存已有请求的 KV Cache，新请求如果拥有相同前缀，可以跳过这部分前缀的重复计算。参考：[vLLM Automatic Prefix Caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)。

## 不同 Agent 之间能否共享 Prompt Cache？

### 参考回答

**可以。只要不同 Agent 的模型请求具有可复用的相同 Prompt 前缀，并且处在允许共享的缓存作用域内，就可以命中同一份 Prompt Cache。**

例如：

- Agent A：$P_{\text{shared}} + P_A$
- Agent B：$P_{\text{shared}} + P_B$

其中 $P_{\text{shared}}$ 可以包含相同的系统指令、工具定义、共享知识或历史上下文。如果底层缓存系统识别到这一段渲染后的输入前缀完全一致，就可以复用此前为该前缀保存的计算状态；从 $P_A$ 与 $P_B$ 开始分叉的部分则需要分别计算。

这里的共享通常不是“Agent A 主动把 Cache 传给 Agent B”，而是 Serving / API 层根据请求前缀自动完成匹配与复用。因此 Agent 的逻辑身份本身通常不是 Cache Key；真正重要的是：

1. 实际送入模型的渲染后前缀是否一致；
2. 模型及相关推理配置是否兼容；
3. 缓存是否仍然有效且当前请求能够访问；
4. 服务端是否设置了租户隔离、Cache Key、Salt 等共享边界。

所以两个 Agent 的 Prompt 只是“语义相同”并不足够。只要 Token、工具定义、消息顺序或其他会改变渲染后前缀的内容不同，就可能无法命中同一缓存。

以 OpenAI API 为例，官方文档明确说明 Prompt Caching 按模型渲染后的完整上下文进行前缀匹配，并可包含开发者消息、工具定义和对话历史。参考：[OpenAI Prompt Caching](https://developers.openai.com/zh-Hans/api/docs/guides/prompt-caching)。

## 为什么用户后续输入相同 Prompt，缓存命中率仍然不是 100%？

### 参考回答

核心原因是：

> **“这一轮用户消息与以前相同”不等于“这一轮送入模型的完整输入与以前相同”。Prompt Cache 匹配的是完整输入从开头开始的可复用前缀，而不是在历史消息中查找重复句子。**

例如第一次请求可能是：

- System
- User：$P$

模型回答后，再次输入完全相同的 $P$，第二次请求实际更接近：

- System
- User：$P$
- Assistant：$R$
- User：$P$

最后一条 User 消息虽然文本仍然是 $P$，但它已经位于新的对话历史之后，所在位置与前序计算状态都发生了变化，因此不能因为“字符串以前出现过”就直接把它当作已缓存输入。

如果第二次请求中有 $N$ 个 Token 属于能够复用的历史前缀，同时又新增了 $M$ 个 Token，那么按最直观的命中率定义：

$$
\text{Cache Hit Rate}
=
\frac{N}{N+M}
$$

只要本轮存在新增且未缓存的输入，即 $M>0$，就有：

$$
\text{Cache Hit Rate}<100\%
$$

因此在正常多轮对话中，更常见的情况是“**历史前缀大量命中 + 当前新增后缀重新计算**”，而不是每一轮都达到 100%。

除此之外，即使两个请求看起来几乎一致，命中率仍可能受缓存粒度与断点、最小可缓存长度、缓存过期或淘汰、请求路由、模型或工具配置变化，以及服务端缓存隔离策略影响。不同服务商还可能采用不同的 cached token 统计与取整方式，因此“完整前缀成功复用”和界面上显示“100%”也不一定完全等价。

参考：[OpenAI Prompt Caching](https://developers.openai.com/zh-Hans/api/docs/guides/prompt-caching)。

## 模型部署如何权衡吞吐、延迟、显存、稳定性与成本？

### 思路

部署的核心是：线上推理服务是否可靠。

- 性能能否承受线上流量：QPS、并发数、首 Token 延迟、整体生成速度、P95 / P99 延迟。
- 资源与成本是否可控。
- 服务是否稳定可靠。
- 是否可观测、可治理。

### 回答

真正要关心的不是模型能否成功加载、跑通一次推理，而是**在目标 SLA（服务等级协议）和成本约束下，能否稳定承载真实线上流量。**

1. **延迟与吞吐**：区分首 Token 延迟和后续生成速度；测试不同并发下的 P95、P99，而非只看单请求平均延迟。关注每秒请求数和每秒生成 Token 数，并通过动态批处理提高 GPU 利用率。
2. **显存**：不能只计算模型权重，还要考虑 KV Cache、中间计算和 Batch 的显存占用。KV Cache 会随并发和上下文长度增长，因此单请求能跑不代表高并发下仍能运行。
3. **调度与资源利用**：考虑长短请求分流、Batch 组织方式和超长上下文限流；否则少量长请求就可能拉高整体尾延迟。
4. **效果回归**：量化、张量并行等优化虽能降低显存或提高吞吐，但必须在真实业务评测集上确认模型质量没有明显退化。
5. **稳定性与成本**：关注超时、OOM、故障恢复、负载均衡、扩缩容、GPU 利用率和单请求成本，并建立完整监控。

> **不是让模型跑起来，而是在保证模型效果的前提下，将吞吐、延迟、并发、显存、稳定性和成本平衡到符合业务要求。**
