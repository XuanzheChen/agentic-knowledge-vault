## TransitScholar Agent 有哪些工具？它们分别有什么用？

**先区分工具与动作：** 当前 Agent 不是让 LLM 自由调用一组 Python 函数。它先由固定 Role 生成结构化输出，代码转换成 Action，经过 `ActionValidator` 校验后由 `ActionExecutor` 执行。在内置 Role 中，**只有 QueryPlanning 被允许使用命名工具 `retrieve_knowledge`**；其余角色主要通过受控 Action 修改研究账本。

### 一、知识检索工具：负责找资料

| 工具 | 用途与当前接入情况 |
| --- | --- |
| `retrieve_knowledge` | **默认 Agent 的统一检索入口。** 接收已有 ResearchQuery，让检索规划器选择 Schema、Wiki、Paper RAG 的组合，校验策略后执行并返回检索结果与诊断。 |
| `search_schema` | 按论文和字段读取已抽取的结构化 Schema，例如方法、数据集、实验指标；返回字段值和来源记录，**不直接当作已采纳 Evidence**。 |
| `search_wiki` | 搜索 Base/Agentic Wiki 的知识页面与概念关系，也能发现相关论文 ID，供后续 RAG 缩小范围。 |
| `search_rag` | 在指定论文内检索原文 Chunk，返回文本、页码、Block/字符位置和检索来源，用于构造候选 Evidence。 |
| `search_workspace_rag` | 在整个 Workspace 的论文间检索、统一候选并重排。**接口已实现，但需要额外注入 `WorkspaceRagRetriever`；默认 RuntimeFactory 没有接入。** |
| `inspect_evidence` | 检查已有 Evidence 是否仍属于当前 Workspace、论文是否有权访问，然后返回该证据；不是联网搜索或自动判断论证正确性。 |

这里的 `search_*` 和 `inspect_evidence` 是 `KnowledgeToolService` 提供的**内部/直接服务接口**，不是默认全部暴露给 LLM 的工具列表。通常由 `retrieve_knowledge` 在经过 `HybridKnowledgeRetrievalPlanner`、`StrategyValidator` 后调度其中的检索路径。参见：[工具定义](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/layer3/tools/contracts.py#L40)、[工具实际实现](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/layer3/tools/service.py#L53)、[默认服务装配](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/product/runtime.py#L125)。

### 二、结构化 Action：负责操作研究状态

| Action | 谁能执行、具体做什么 |
| --- | --- |
| `CREATE_QUERY`、`RETRIEVE_QUERY` | QueryPlanning：将研究子问题登记到 Query Ledger，并调用 `retrieve_knowledge` 检索。**默认 ActionPlanner 会生成这两种动作。** |
| `UPDATE_QUERY` | QueryPlanning：更新已有 Query 的状态，例如完成或放弃；**协议与执行器支持，但默认 ActionPlanner 不自动生成**。 |
| `ADMIT_EVIDENCE` | EvidenceReasoning：从本轮检索候选中选定 Evidence，校验 Query/来源后写入 Evidence Ledger。 |
| `CREATE_CLAIM`、`LINK_EVIDENCE` | ClaimReasoning：建立论点，并将它与**已采纳** Evidence 关联，形成可追溯的支持关系。 |
| `UPDATE_CLAIM` | ClaimReasoning：更新已有论点的状态或理由；**协议与执行器支持，但默认 ActionPlanner 不自动生成**。 |
| `INVOKE_ROLE`、`FINISH_SESSION` | ResearchCoordinator / FinalSynthesis 的允许动作中有这些类型；但**当前默认主循环用 `next_role_id` 切换角色、直接处理终局**，并不通过这两个 Action 完成常规流程；默认 `role_invoker` 还是空回调。 |

实际自动产生的核心链条是：

`QueryPlanning → CREATE_QUERY / RETRIEVE_QUERY → KnowledgeToolService → EvidenceReasoning → ADMIT_EVIDENCE → ClaimReasoning → CREATE_CLAIM / LINK_EVIDENCE → FinalSynthesis`。

需要注意，检索命中不等于已采纳证据，已采纳证据也不等于 Claim 的科学结论成立。每个 Action 都要检查 Role 的 `allowed_actions` / `allowed_tools`、Run/Session/Workspace 归属，以及 Query、Evidence、Claim 是否存在，模型不能绕过这些边界直接写数据库。

参见：[Action 类型](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/layer3/actions/models.py#L14)、[Role 工具和动作权限](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/layer3/roles/builtin.py#L72)、[默认 ActionPlanner](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/product/roles.py#L67)、[Action 校验](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/layer3/actions/validation.py#L25)、[Action 派发](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/layer3/actions/executor.py#L26)、[默认角色调度方式](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/layer3/runtime/main_runtime.py#L275)。

## 工具和Action对所有role都开放吗？每个role都能使用什么工具，都能采用哪些Action？

**不对所有 Role 开放。** 每个 Role 在注册时都有独立的 `allowed_tools`（允许调用的命名工具）和 `allowed_actions`（允许执行的状态操作）。默认 Session 的五种 Role 权限如下：

| Role | 可用的命名工具 | 允许的 Action | 主要用途 |
| --- | --- | --- | --- |
| `ResearchCoordinator` | 无 | `INVOKE_ROLE`、`FINISH_SESSION` | 选择下一职能，或决定结束 Session |
| `QueryPlanning` | `retrieve_knowledge` | `CREATE_QUERY`、`UPDATE_QUERY`、`RETRIEVE_QUERY` | 创建/更新查询并检索论文知识 |
| `EvidenceReasoning` | 无 | `ADMIT_EVIDENCE` | 从检索候选中采纳证据并写入账本 |
| `ClaimReasoning` | 无 | `CREATE_CLAIM`、`UPDATE_CLAIM`、`LINK_EVIDENCE` | 创建或更新论点，绑定已采纳证据 |
| `FinalSynthesis` | 无 | `FINISH_SESSION` | 根据已保存的 Claim 和 Evidence 生成带引用的结论 |

这是**允许权限表**，不等于默认运行时每种 Action 都一定会被执行。当前 `BuiltinRoleActionPlanner` 实际自动生成的是：QueryPlanning 的 `CREATE_QUERY + RETRIEVE_QUERY`、EvidenceReasoning 的 `ADMIT_EVIDENCE`、ClaimReasoning 的 `CREATE_CLAIM + LINK_EVIDENCE`；`UPDATE_QUERY`、`UPDATE_CLAIM` 虽有协议和执行器实现，但默认规划器不自动生成。ResearchCoordinator 通过 `next_role_id` 切换职能，FinalSynthesis 由主循环完成终局处理，通常不执行 `INVOKE_ROLE` 或 `FINISH_SESSION` Action。参见：[五种 Role 的权限定义](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/layer3/roles/builtin.py#L72)、[默认 ActionPlanner](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/product/roles.py#L67)、[主循环的职能切换](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/layer3/runtime/main_runtime.py#L410)。

**为什么要限制？** 因为不同 Role 的职责不同：检索角色不应直接改 Claim，论点角色也不应绕过证据采纳直接检索或写入 Evidence。代码在 `ActionExecutor` 真正执行前调用 `ActionValidator`，检查 Role 是否允许该 Action；对 `RETRIEVE_QUERY` 还校验 `tool_name` 是否在 `allowed_tools` 中，并检查 Workspace、Run、Session 及所引用对象的归属。**仅在 Prompt 中要求模型守规矩还不够，真正的权限边界由 Python 代码执行。** 参见：[ActionValidator](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/layer3/actions/validation.py#L25)、[ActionExecutor](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/layer3/actions/executor.py#L44)。

此外，Run 级的 `RunCoordinatorRole` 是另一层协调器：它输出 `direct_session / planned_research / complete` 等 `RunDecision`，**不属于上表的五个 Session Role，也不使用这些 Session Action 权限**。参见：[RunCoordinatorRole](https://github.com/XuanzheChen/transit-scholar/blob/d077fb89aded267bc7dc1e5fe33ec6b1e6504c49/src/transit_scholar/layer3/roles/run_coordinator.py#L155)。
