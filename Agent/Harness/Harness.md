Harness 是围绕模型决策的运行时控制层：模型负责提出动作，Harness 负责状态流转、执行许可、资源预算、失败恢复和审计。以下内容根据 2026-11-06 的十组 Agent Harness 问答归纳，为**工程设计参考回答**，不是对某个实际项目已经实现这些机制的声明。机制与阈值应结合具体工具语义、风险和实验结果确定。

## Agent Loop 如何设计，除 max_turns 外还应有哪些终止条件？

### 参考回答

Agent Loop 是一个受运行时控制的状态机，不是无界的“模型输出 → 工具执行”循环。基本路径如下：

```text
用户任务 → 加载 Task State / Context → LLM 决策
       → [工具调用] 校验 / 执行 / 回灌 → 更新状态 → 继续判断
       → [最终回答] 验收任务是否真正完成
       → [暂停/终止] 持久化状态与终止原因
```

除 `max_turns`，还需要控制：

| 控制条件 | 防止的问题 |
| --- | --- |
| 任务完成及验收条件 | 模型说“完成”但环境目标实际未满足 |
| Token / API 成本预算 | 上下文与模型调用开销失控 |
| 整体 Deadline 与单次模型/工具 Timeout | 卡死、长期占用资源 |
| 连续错误数、每类错误重试上限 | 无效重试风暴 |
| 无进展阈值与循环检测 | 多轮重复调用但没有实质变化 |
| 用户取消、权限拒绝、安全规则 | 已不应继续的动作继续执行 |
| 人工审批与外部事件等待 | 需要暂停而非继续占用 Worker |

设计上必须区分 `SUCCESS`、`FAILED`、`BUDGET_EXCEEDED`、`TIMEOUT`、`STALLED`、`CANCELLED` 和 `WAITING_APPROVAL` 等状态：**Loop 停下不等于任务成功**。验收条件应优先由测试、文件状态、业务规则等外部证据决定，而非仅靠模型自报完成。

更基础的执行范式与状态分类见 [[Agent/Agent#Agent 如何通过状态和执行循环完成任务？|Agent 的状态与执行循环]]；为什么需要 Runtime 约束见 [[Agent/Agent#ReAct 执行循环为什么需要运行时约束？|ReAct 的运行时约束]]。

## 模型返回 Tool Call 后，如何校验参数、控制权限、沙箱执行并回灌结果？

### 参考回答

模型返回的 `tool_call` 只是**调用意图**，不能直接等于执行授权。一个 Tool Dispatcher 可以依次处理：

1. **参数校验**：使用工具注册时的 JSON Schema 检查类型、必填项、枚举和边界，并执行路径、URL、目标实体存在性等语义校验。参数错误返回结构化错误，供模型修正；不运行目标工具。
2. **权限与风险校验**：根据 Agent 身份、用户授权、工作区范围和工具能力实施最小权限。只读操作可自动放行；删除、外传、部署等高风险操作按策略拒绝或请求人工审批。不能依赖 Prompt 保证授权。
3. **沙箱执行**：隔离文件系统、网络与进程能力，设置 Timeout、CPU/内存与输出大小上限。对文件路径穿越、符号链接替换和校验后资源变化等问题，最终应由文件描述符级操作、OS 权限或沙箱强制边界，而不是只做字符串检查。
4. **结果回灌**：规范化为 `status`、`output`、`error`、`duration`、`artifact_ref` 等字段，必要时截断和脱敏，通过对应 `tool_call_id` 写入消息或事件记录，再进入下一轮。应保持工具调用与结果的协议关联，不丢失失败信息。

```text
LLM tool_call
   ↓ Schema / 业务校验
   ↓ 权限与审批 Policy Enforcement
   ↓ 沙箱中执行
   ↓ 结果结构化、脱敏、存证
   ↓ tool_call_id 匹配 → 更新 State → 继续 Agent Loop
```

对有副作用的工具，执行前应先持久化调用意图；遇到超时/崩溃，要结合幂等键或外部执行状态决定能否重试。工具返回的网页、日志、文件同样属于不可信输入，不能因此提升其指令权限。

## 如何检测 Agent 重复调用工具或陷入死循环，并完成去重与回退？

### 参考回答

可组合**状态指纹、进展检测和分级恢复**，但重复调用本身并不必然代表异常。

状态指纹可取 `hash(tool_name, normalized_args, relevant_environment_version, task_phase)`：参数先规范化，环境版本可用文件 Hash、工作区 Diff、远端任务状态或错误类别表示。Harness 在滑动窗口中检测同一状态反复出现，或 A → B → A → B 等周期模式。仅凭相同工具名称不应直接报错。

进展指标要与任务目标相连，例如新文件 Diff 是否有效、失败测试是否减少、外部任务是否向完成状态推进、子目标是否完成。连续多轮**状态没有变化且目标没有进展**时才判定为停滞。

| 场景 | 处理方式 |
| --- | --- |
| 同参数只读查询，数据版本未变 | 缓存或复用结果，减少重复成本 |
| 有幂等保障的写操作 | 使用业务幂等键与执行记录去重 |
| 无法确认结果的非幂等操作 | 不盲目重试，先查询执行状态或人工接管 |
| 初次停滞 | 回灌重复与失败证据，提示模型换策略 |
| 持续停滞 | 回到有效 Checkpoint，重新规划或换工具 |
| 多次恢复仍无进展 | 终止为 `STALLED`，保留证据供人工处理 |

**例外**：异步轮询、等待构建或部署完成，本来就需要重复查询。此时应设置合法轮询窗口、间隔退避和总 Deadline，不将“重复”误判为死循环。回退对话历史不等于回滚外部副作用；文件、数据库等变更需要真实撤销或补偿。

## Agent 运行中服务重启，Checkpoint 存什么、放哪里、如何恢复？

### 参考回答

Checkpoint 不只是对话历史，应保存足够重建执行状态的信息：

- **运行身份与位置**：`run_id`、`task_id`、当前状态/步骤、轮次、工作流版本。
- **上下文与计划**：任务目标、约束、消息历史或摘要引用、待办、决策记录。
- **工具执行账本**：`tool_call_id`、参数 Hash、执行状态（`PENDING` / `RUNNING` / `SUCCEEDED` / `FAILED`）、幂等键、结果引用及重试计数。
- **资源与外部引用**：Token / 成本消耗、截止时间、工作区版本、外部 Job ID、Artifact / 日志地址。

存储上，单机可用 SQLite + 本地持久化文件；分布式可采用 PostgreSQL 保存结构化状态与执行记录、对象存储保存大型 Artifact，Redis 仅用于热缓存、Lease 或协调。关键状态不能只保存在进程内存或易失缓存。

恢复流程为：扫描未完成 Run → 获取独占 Lease → 载入最新有效 Checkpoint → 重建 Context / State → **核对在途工具调用的真实结果** → 从安全边界继续。若工具已经成功且结果有记录，直接回灌；若未开始，可以重新调度；若结果未知，先通过外部 Job ID 或业务键查证。对无可验证幂等保障的高风险操作应暂停并交人工。

特别注意：调用外部系统的副作用与本地数据库更新通常无法放进单一原子事务，因此更现实的是“**至少一次调度 + 幂等执行 + 状态核对 / 补偿**”，而不是承诺所有工具天然 Exactly-Once。

## Human-in-the-Loop 审批被拒绝或超时后，任务怎样续跑与兜底？

### 参考回答

把 Human-in-the-Loop（HITL）建模为可持久化的异步审批节点：运行到审批前，将任务标记为 `WAITING_APPROVAL`，记录 Checkpoint、`approval_id`、待操作参数、审批范围和过期时间，释放 Worker，而不是在循环中阻塞等待。

**拒绝**意味着当前操作不获授权：将 `REJECTED` 和原因回灌 Agent，允许重新规划合法替代路径；没有可行替代方案时进入 `BLOCKED`。不能把“换个工具做同一件未经授权的事”当作降级。

**超时**应默认遵守风险策略：删除、支付、部署或对外发送数据等高风险动作采用 Fail Closed（未获批准则不执行）；低风险只读操作仅在既有授权范围内继续；必须依赖人类决策时暂停并通知，不把沉默视为同意。

**批准后续跑**：核验用户身份与审批有效期 → 用 CAS / 事务原子消费审批 → 重新获得 Worker Lease → 载入 Checkpoint → 复核操作参数、权限与环境版本 → 执行 → 回灌。审批应绑定具体参数或参数摘要，参数发生实质变化必须重新授权；超时后迟到的批准不能重新激活已失效的审批。

## 工具结果过大或执行失败时，如何截断、重试、熔断并保证幂等？

### 参考回答

**输出治理**不等于直接截取前 N 个字符。对每个工具设置最大字节数与 Token 预算，按语义保留有效部分：日志保留错误栈、关键上下文和尾部；搜索返回排名较高且不同来源的证据；大文件可按段落/块摘要。原始输出持久化为 Artifact，回灌 `artifact_id` / 路径 / 行号或 Hash，以便后续精确读取。摘要要保留证据引用，不能替代需要逐字核对的原始日志或代码。

**重试**先按错误分类而不是“失败就重试”：网络波动、限流、503 等可在可重试且安全的条件下使用有限次数的指数退避和 Jitter；Schema 错误、权限拒绝属于不可直接重试；命令执行成功但测试失败属于任务层反馈，应交给 Agent 修复，而不是工具执行器机械重跑。

**熔断**通常按下游服务或工具配置 `CLOSED → OPEN → HALF_OPEN`：失败率/连续异常超阈值后暂时拒绝并降级，冷却后允许少量探测，再决定恢复。避免并发 Agent 同时冲击故障下游。

**幂等**方面：只读操作通常可安全重复；幂等写入使用稳定 `idempotency_key` 与执行记录；非幂等操作则需要业务层支持幂等、结果查询或补偿。最危险的情形是“工具已完成副作用，但响应丢失”：此时执行状态未知，不能无条件再发一次请求。

推荐为调用保存统一记录：`tool_call_id`、`arg_hash`、`idempotency_key`、`status`、`attempt`、`error_type`、`artifact_ref`、`duration`。这套账本也服务于 Checkpoint 恢复和审计。

## 工具很多时，如何检索候选工具并按需加载 Schema？

### 参考回答

工具规模较大时，不应在每轮 Context 一次性注入数百份 Schema。可以使用 **Tool Registry → 检索 → Lazy Loading → 再校验** 的机制：

1. Registry 维护工具名称、能力描述、参数 Schema、权限范围、所属 MCP Server 和使用成本等元数据。
2. 首轮只常驻少量核心工具，如 `search_tools`；根据任务描述使用关键词/BM25 与语义召回，再选择性 Rerank，得到 Top-K 候选。
3. 把当前任务阶段需要的完整 Schema 加入模型 Context，任务阶段变化时按需增减；常用工具可缓存，避免反复检索。
4. 在工具发现阶段过滤未授权能力，在实际执行时**再次校验权限**，不能把“查到了工具”视为“获准执行”。

例如查询 GitHub PR 时，模型可能只需 PR 查询、差异读取和评论相关工具，而不需要加载所有数据库、部署或文件系统工具。

质量评估可看 `Tool Recall@K`（正确工具有没有进入候选）、`Tool Selection Accuracy`（模型是否选对）、Token 成本与端到端延迟。检索不充分时应允许扩大候选范围，避免过早把正确工具排除。

**概念边界**：Function Calling 解决模型怎样以结构化参数表达工具调用；MCP 解决外部能力如何统一发现和接入。二者可以组合，而工具检索与按需加载是 Harness 的 Context / Tool Governance 设计，不是 MCP 自动替应用完成的。详见 [[Agent/通信协议/通信协议#MCP、Function Calling 与 Code Mode 有什么区别？|Function Calling、MCP 与 Code Mode]]。

## 如何防御 Prompt Injection、拦截危险工具调用并保护敏感数据？

### 参考回答

Prompt Injection 的风险是**低信任内容越过边界，影响高权限指令或工具行为**。浏览器页面、README、日志、MCP 工具输出、检索结果都应作为外部数据处理，保留来源与信任等级，不把其中的命令当作 System / Developer 指令。检测器可以辅助发现攻击，但不能作为唯一防线。

在 Tool Dispatcher 设置独立的 Policy Enforcement Point，按工具能力、目标资源、数据敏感度和用户授权作决策：只读低风险操作在既有权限范围自动执行；写入/修改受工作区和沙箱限制；高风险删除、外发敏感信息或生产部署需要明确授权。Shell 命令拦截不能只靠危险词黑名单，要依赖执行沙箱、OS 权限、网络出口限制和可审计策略。

**数据保护**分输入、执行、输出和外传四个环节：

- 输入和工具输出识别密钥、Token、个人信息；在确有业务需要时遮蔽、令牌化或阻止暴露给 LLM。
- 密钥放 Secret Manager，由受信任的 Tool 在执行时按需读取；模型侧尽量只保留不含密钥的引用。
- 对日志、模型输出和工具返回进行敏感内容检查，防止调试信息带出凭据。
- 发送邮件、HTTP 请求、上传文件等外传动作，检查接收方、域名、数据分类和授权范围。

需要区分“**模型被诱导提出危险动作**”与“**执行层允许危险动作真正发生**”：Harness 无法保证模型永远不受干扰，但可以通过最小权限和确定性策略让违规操作无法越权执行。检索、摘要和二次模型审查同样不能替代底层授权。
