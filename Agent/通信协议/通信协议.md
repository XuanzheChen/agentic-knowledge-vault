## MCP、A2A、ANP 分别解决什么问题？

Hello Agents 可以提供一个很好的第一层理解：**MCP 解决 Agent 如何接入外部能力，A2A 解决独立 Agent 如何协作，ANP 进一步面向开放网络中的 Agent 身份、发现与跨域连接。**

| 协议 | 核心通信对象 | 主要解决的问题 | 更适合记成什么边界 |
| --- | --- | --- | --- |
| MCP（Model Context Protocol） | Agent Host / Client ↔ Tool、Data、Resource、Service | 如何用统一方式发现和调用外部能力 | **能力边界（Capability Boundary）** |
| A2A（Agent2Agent Protocol） | 独立 Agent ↔ 独立 Agent | 如何发现能力、委托任务、交换消息、跟踪任务并交付结果 | **自治体边界（Autonomy Boundary）** |
| ANP（Agent Network Protocol） | Agent ↔ 开放 Agent 网络 | 如何建立身份、发布能力、发现其他 Agent，并进行跨域通信 | **网络边界（Network Boundary）** |

可以把三者先理解为：

```text
MCP：我已经知道我要使用什么能力，怎样标准化地接入它？
A2A：我把目标委托给另一个独立 Agent，双方怎样标准化协作？
ANP：开放网络里有哪些 Agent、它们是谁、能做什么、怎样找到并连接？
```

实际系统对三者的使用并不是泾渭分明的。A2A 与 ANP 在能力描述、发现和通信方面也存在交叉，只是关注中心不同：**A2A 更偏 Agent interoperability 与任务协作，ANP 更偏 Agentic Web / Agent Network 的身份与网络基础设施。**

截至 2026 年 9 月，三者的工程成熟度也不同：MCP 已经形成很广泛的工具接入生态；A2A 最新正式规范为 1.0.0，已经面向生产互操作；ANP 已发布 1.1 的身份、描述、发现等规范，但部分通信子规范仍处于 Draft，整体生态明显更早期。

## MCP 是什么，它在现代 Agent 工程中的定位是什么？

MCP（Model Context Protocol）是一套让 AI 应用以统一方式接入外部工具、数据与服务的开放协议。它真正解决的不是“让 LLM 学会调用函数”，而是**不同 Agent Host 与不同能力提供方之间的互操作问题**。

没有统一协议时，每个 Agent Host 都可能分别适配 GitHub、数据库、文件系统、浏览器和业务 API：

```text
Host A × GitHub
Host A × Database
Host A × Browser
Host B × GitHub
Host B × Database
Host B × Browser
```

MCP 把这种 N×M 集成拆成统一的 Client / Server 边界：能力提供方通过 MCP Server 对外暴露能力，Host 侧通过 MCP Client 发现并调用它们。

```text
Agent Host
   │
MCP Client
   │
   ├── MCP Server → GitHub
   ├── MCP Server → Database
   └── MCP Server → Internal API
```

因此 MCP 更适合被理解为一种**能力标准化暴露与接入协议**。对 Agent 来说，对端不一定是另一个 Agent，也不需要具备自主规划或任务生命周期；它完全可以只是数据库、搜索服务或普通业务 API 的适配层。

## A2A 是什么，它与 MCP 的边界在哪里？

A2A（Agent2Agent Protocol）是一套面向**独立、可能完全不透明的 Agent 系统**的互操作标准。它假设通信双方可以使用不同模型、不同框架、不同语言，甚至来自不同厂商，而且不需要暴露自己的内部 Prompt、Memory、Tool 或执行逻辑。

A2A 的关键不是“两个 LLM 可以聊天”，而是：**一个 Agent 可以把任务委托给另一个自治系统，并以统一方式管理这段协作。**

当前 A2A 规范中的几个重要抽象包括：

- **Agent Card**：描述 Agent 的身份、能力和可用交互方式，相当于对外服务说明。
- **Message**：双方交换的消息。
- **Task**：有 ID 和状态生命周期的工作单元，可以经历 submitted、working、input-required、completed 等阶段。
- **Artifact**：任务最终产生的文件、结构化数据或其他成果。
- **Streaming / asynchronous updates**：支持长时间任务持续汇报状态，而不是把协作压缩成一次同步 RPC。

因此，是否需要 A2A 不取决于“代码里定义了几个 Agent”。如果 Planner、Coder、Reviewer 都由同一个 Runtime 管理，接口固定、状态由上层统一维护，那么普通函数、队列、RPC、HTTP API 或框架内部消息机制通常已经足够。

当对端真正成为一个独立自治服务时，A2A 的价值才明显：例如它自己维护任务状态、可以反问调用方、长时间执行、产生多个 Artifact，并且调用方不应该依赖它的内部实现。

MCP 与 A2A 因而是互补关系：

```text
Agent A ── A2A ──> Agent B
  │                   │
 MCP                  MCP
  │                   │
Tools A             Tools B
```

**MCP 解决 Agent-to-tool，A2A 解决 Agent-to-agent。**

## ANP 是什么，它与 A2A 有什么关系？

ANP（Agent Network Protocol）把问题继续扩展到开放网络：当 Agent 数量很多、分属不同域和平台，而且调用方甚至不知道应该找谁时，首先要解决的就不只是“怎样发送一个 Task”。

ANP 关注的问题包括：

- 一个 Agent 如何拥有可验证的网络身份；
- 如何发布自己的能力和接口描述；
- 其他 Agent 如何主动或被动发现它；
- 跨域 Agent 如何建立消息通信和安全关系；
- 在更大的 Agent 网络中如何形成可扩展的互联机制。

ANP 1.1 已经包含 `did:wba` 身份体系、Agent Description、Agent Discovery 等规范。其 Agent Discovery 使用 `.well-known` 等机制发布和发现 Agent 描述，也支持面向搜索服务的被动发现。这使 ANP 更接近在回答：**如果未来存在一个开放的 Agent Internet，身份、目录、发现和跨域通信基础设施应该怎样设计？**

A2A 与 ANP 并非完全互斥。A2A 自己也包含 Agent Card 和能力发现，ANP 也会涉及 Agent 间消息。因此更准确的区别不是“一个会发现、一个不会发现”，而是关注中心：

- **A2A：已进入协作关系的独立 Agent 怎样委托任务、交换消息并交付 Artifact。**
- **ANP：开放网络里的 Agent 怎样建立身份、发布能力、被发现并形成跨域网络。**

如果一个系统里的 Agent 都是预先配置好的内部组件，通常没有必要引入 ANP。只有当系统真正需要动态寻找未知 Agent、跨组织建立身份与连接时，它才进入 ANP 的核心问题空间。

## MCP、Function Calling 与 Code Mode 有什么区别？

这三个概念经常一起出现，但它们不属于同一层：**Function Calling 是模型 API 的工具调用原语，MCP 是能力互操作协议，Code Mode 是工具执行与编排范式。** Function Calling 和 Code Mode 本身都不是 MCP 的替代协议。

### Function Calling：模型怎样表达“我要调用这个工具”

Function Calling（也常称 Tool Calling）由模型 API 提供。应用把函数名称、说明和参数 Schema 告诉模型，模型根据用户请求生成结构化的工具调用及参数；真正的函数执行仍由宿主应用完成。

```text
Application 提供 tool schema
          ↓
         LLM
          ↓
  tool_call(name, args)
          ↓
Application 执行真实函数
```

因此 Function Calling 解决的是**模型输出与宿主程序之间的结构化调用接口**。具体工具从哪里来、怎样远程发现、如何认证和跨应用复用，并不是 Function Calling 自身解决的问题。

### MCP：工具从哪里来，以及不同应用怎样统一接入

MCP 位于更外层。一个 MCP Server 可以标准化地发布能力，MCP Client 负责发现和调用。Host 拿到 MCP 工具后，完全可以把它们转换成当前模型供应商的 Function / Tool Schema，再通过模型原生 Function Calling 让模型选择调用哪个工具。

因此常见关系其实是：

```text
LLM
 │ Function Calling / Tool Calling
 ↓
Agent Host
 │ MCP Client
 ↓
MCP Server
 ↓
External Service
```

所以：

> **Function Calling 标准化的是“模型怎样提出一次工具调用”；MCP 标准化的是“应用怎样获得、发现和访问外部能力”。**

### Code Mode：让模型写一段程序来编排多个工具

Code Mode 是近年逐渐流行的一种 tool-use pattern。与“模型每调用一次工具就重新推理一次”不同，它给模型一个受控代码执行环境或代码工具，让模型先生成一段程序，在程序中使用循环、条件、并行和数据处理逻辑来组合多个工具，然后只把必要结果返回模型。

直接 Tool Calling 通常类似：

```text
LLM → tool A → LLM → tool B → LLM → tool C → LLM
```

Code Mode 更接近：

```text
LLM → generate code
          ↓
      sandbox runtime
      ├── tool A
      ├── tool B
      ├── filter / loop / branch
      └── tool C
          ↓
      focused result → LLM
```

它尤其适合大工具目录、重复调用、长确定性调用链以及需要在中间结果上做过滤或聚合的任务，因为可以减少 LLM round trip，并避免大量中间结果反复进入模型 Context。代价是需要安全 sandbox、权限治理、可观测性和错误处理，而且当前不少 Code Mode 实现仍属于实验性能力。

Code Mode 与 MCP 同样可以组合：MCP 负责把外部能力接进来，Code Mode 再把这些能力暴露成可编程的 typed methods，由模型写代码组合调用。Cloudflare 的 Code Mode 就明确支持把已有 MCP Client 连接暴露进 Code Mode sandbox，也支持把大量 MCP tools 包装成少数 code/search/execute 类型的模型侧工具。

### 三者放在一起看

| 维度 | Function Calling | MCP | Code Mode |
| --- | --- | --- | --- |
| 本质 | 模型 API 原语 / Tool Calling 机制 | Client-Server 能力互操作协议 | 工具调用与执行范式 |
| 主要问题 | 模型怎样选择工具并生成结构化参数 | 外部工具和数据怎样被发现、接入、调用 | 多个工具怎样用程序化逻辑高效组合 |
| 谁执行真实能力 | Host / Application | MCP Server 背后的实现 | Sandbox 中的模型生成代码调用已有工具 |
| 工具发现 | 通常由应用预先注入 Schema | 协议原生提供统一发现边界 | 可以预先提供 typed API，也可以按需搜索 / 发现 |
| 多步调用 | 常需要多次 Model ↔ Tool 往返 | MCP 本身不决定模型循环方式 | 可在一次代码执行中组合循环、条件、并行和多次调用 |
| 是否是通信协议 | 否 | **是** | 否 |

从 Agent 工程分层看，可以用下面这张图记忆：

```text
                   ┌─────────────────────────┐
LLM tool-use       │ Function Calling       │
strategy           │ 或 Code Mode           │
                   └───────────┬─────────────┘
                               ↓
                   ┌─────────────────────────┐
Capability interop │ MCP                     │
                   └───────────┬─────────────┘
                               ↓
                       Tools / Data / APIs

Independent Agent A ───────── A2A ─────────> Independent Agent B

Open Agent Network：identity / description / discovery / cross-domain communication → ANP
```

因此在做技术选型时，不应该问“Function Calling、MCP、Code Mode 三选一吗”，而应该分别问：**模型如何表达工具调用？外部能力如何统一接入？多步工具调用是否值得改成程序化编排？** 这三个问题可以得到三个不同答案，并同时存在于同一个 Agent 系统中。
