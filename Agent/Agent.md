## Agent 如何通过状态和执行循环完成任务？

### 思路

仿照 Claude Code 的工作流。

![[ClaudeCodeAgenticLoop.png]]

### 参考回答

对话 Agent 可以设计成一个状态驱动系统。核心不是简单地把历史消息送给 LLM，而是维护一个 Agent State。核心状态主要有五类：

1. **会话状态（Conversation State）**：当前对话历史和上下文。
2. **用户状态（User State）**：用户长期偏好和记忆。
3. **任务状态（Task State）**：当前任务目标、执行计划和完成情况；这是 Agent 区别于 Chatbot 的关键。
4. **工具 / 环境状态（Tool / Environment State）**：外部工具调用结果和业务环境状态。
5. **规划状态（Planning State）**：结构化的中间计划和执行结果。

运行时，Agent 根据当前状态和用户输入，由 LLM 或规则 Controller 决定下一步 Action，例如继续追问、调用工具、检索知识或生成答案；执行后更新状态，形成循环。工程上可以用状态机或 LangGraph 一类的图工作流管理状态迁移，并按生命周期将不同状态分别存储在 Context、Checkpoint、数据库和 Memory 系统中。

### 我的总结

核心状态包括会话状态、短期任务状态与长期记忆状态。Agentic Loop 中还存在工具调用状态；对于复杂规划任务，任务状态需要进一步拆分为多个阶段的子任务状态，以及至关重要的 Loop 决策状态。

一个典型流程是：先依据会话状态、任务状态、记忆、用户输入和工具能力构造上下文；然后进入 Agentic Loop，进行上下文治理（如裁剪、压缩），调用 LLM 理解意图、规划任务并决定是否调用工具；再根据工具调用后的状态决定继续循环还是退出。最后输出结果，并更新会话、任务和记忆状态。

### 强化学习视角

用户输入、会话上下文、长期记忆、任务状态和工具能力，会在上下文治理后共同构成 LLM 观测到的环境状态。LLM 可以看作 Policy，基于观测决定 Tool Calling 等 Action；工具结果形成新的 Observation，环境据此决定是否继续循环，同时环境状态持续迭代。

> **State → Policy / LLM → Action → Environment → Observation → New State**

## 从单轮问答到持续对话，需要哪些机制？

核心是将单轮、无状态的问答系统升级为有状态、可持续交互的对话系统。

1. **会话管理**：通过会话标识维护不同用户、不同会话的消息历史。
2. **对话状态管理**：历史消息只记录“之前说过什么”；还需结构化维护当前话题、用户意图和已确认信息，以处理指代、省略、改口和话题切换。
3. **上下文管理**：不能无限把历史消息送给模型，需要历史裁剪、摘要和相关信息的动态召回。
4. **长期记忆**：若希望虚拟角色跨会话认识用户，需独立的长期记忆模块，只保存稳定、有长期价值的信息，并支持更新与过期。
5. **角色设定**：维持身份、语气和行为边界，避免长对话后人格漂移。
6. **多模态与实时交互**：语音或虚拟人产品还需接入 ASR、TTS、表情与口型，并处理流式响应、低延迟和用户打断。
7. **安全与评估**：补充内容安全、隐私，以及多轮一致性、记忆准确率、角色一致性和交互延迟等指标。

> **输入处理 → 会话管理 → 对话状态 → 上下文与记忆 → 角色化生成 → 多模态输出 → 状态更新**

整个系统的本质仍然是把对话做好，而不是让它变成一个执行复杂任务的 Agent。

## 长期记忆应写入什么，如何避免信息污染？

### 参考回答

线上多轮对话中，不应把每一轮内容都直接写入长期记忆，而应先区分当前会话、当前任务状态和真正需要长期保存的信息。长期记忆只保留稳定、可复用且来源明确的信息，例如用户长期偏好；“今天有点累”这类临时信息通常只留在当前会话中。

写入前需要完成去重、冲突判断和敏感信息检查。新信息与旧记忆冲突时，应更新或覆盖旧记忆，而非持续追加；还应为部分记忆设置有效期和置信度，避免过时信息长期存在。读取时也不能把所有记忆都放入上下文，而应只取与当前问题相关、可信且较新的部分。

> **少写、分类写、可更新、会过期、按需读。**

### 我的理解

首先建立一套记忆存储格式，标明记忆的来源、置信度和生存期。分析用户消息，判断它属于临时信息还是长期可记忆信息，并赋予相应生存期。

信息写入记忆库前，需要检测与既有记忆是否冲突；存在冲突时进行更新或覆盖。但若信息是 LLM 根据用户消息推断而来，则应赋予低置信度；即使与原有记忆冲突，也不应直接覆盖原记忆。

这里保留的是 Agent 侧的基础写入原则；Memory Formation、检索、聚合、遗忘以及具体框架实现见 [[Memory#工程化 Agent Memory 的核心问题是什么？|工程化 Agent Memory 的核心问题是什么？]]。

## 对话中的意图、约束和状态冲突如何处理？

### 思路

按照软冲突和硬冲突分别处理：软冲突是指令、规则或状态层面的冲突；硬冲突涉及工具调用和安全边界，不应受提示词直接影响。

### 初步理解

对于软冲突，例如用户偏好、项目规划和历史记忆之间的不一致，可以采用叠加而非立即覆盖的方式，将信息放入上下文中处理。由于语言本身存在模糊性，后注入的信息通常更容易被模型关注，但这种结果并不完全确定。

对于硬冲突，例如工具调用或安全层面的冲突，应通过系统 Harness 控制，使用户提示词无法绕过约束。工具可以划分为三类：可直接执行、需要用户确认、完全拒绝执行；以规则为准处理与用户提示词之间的冲突。

### 参考回答

这个问题本质上是对话状态的一致性问题。系统不应只依赖完整 Chat History，而应维护结构化的 Task State，例如用户目标、关键 Slot、约束和当前待执行动作。每一轮输入解析出新的 Intent 和 Constraint 后，先与现有状态进行冲突检测。

- 用户明确修改先前要求时，例如“3 点改成 5 点”，最新且明确的指令覆盖旧状态。
- 仅出现新实体、但无法确定是否修改任务状态时，不直接覆盖。
- 新旧要求无法同时满足时，进入澄清环节，让用户决定优先级。

还要考虑指令优先级：新的用户指令可覆盖旧用户偏好，但不能覆盖系统安全规则和业务不变量。所有冲突消解后，再更新统一的 Conversation State；后续 Planner 和 Tool Execution 只基于这个规范状态执行。

> **明确修改自动覆盖；模糊冲突向用户确认；高优先级规则不可被低优先级指令覆盖；状态更新必须显式、可追踪。**

### 我的总结

这是一个对话状态一致性问题：用户意图可能与 Agent 保存的会话状态、任务状态、长期记忆或 Memory 不一致。首先通过语义理解判断这种不一致是单纯差异、真正相悖，还是存在歧义。

- **单纯差异**：例如突然提出一个枝节问题，正常回答即可。
- **存在歧义**：Agent 应主动追问，确认是差异还是冲突。
- **真正相悖**：进一步判断冲突层级。

如果与安全等高级规则冲突，应优先遵守高级规则：不可放行的直接拒绝；可降级或需要确认的，可要求二次确认、部分执行或降级执行。若只与短期会话或任务状态冲突，则应以用户最新意图为准；在上下文治理中将旧意图标记为过时，以新意图作为唯一可信状态，同时留存变更证据。

## ReAct、Plan-and-Solve 与 Reflection 在 Agent 中分别是什么意思？

这三者首先不是具体开发框架，而是组织 Agent **“如何决定、行动和修正”** 的三种经典执行范式。它们最核心的区别在于：**什么时候做规划，以及什么时候根据结果改变后续决策。** [Hello-Agents 第四章](https://hello-agents.datawhale.cc/#/./chapter4/%E7%AC%AC%E5%9B%9B%E7%AB%A0%20%E6%99%BA%E8%83%BD%E4%BD%93%E7%BB%8F%E5%85%B8%E8%8C%83%E5%BC%8F%E6%9E%84%E5%BB%BA)

### ReAct：边观察、边决策、边行动

ReAct（Reasoning + Acting）把推理和行动交错在同一个循环里：Agent 根据当前上下文决定下一步 Action，调用工具或作用于环境，获得新的 Observation，再根据新观察重新决定下一步。因此它不是“一开始想完再做”，而是典型的**走一步看一步**。

> **Thought / Decision → Action → Observation → 新一轮 Decision → ... → Finish**

它特别适合搜索、浏览器操作、排障等路径事先不完全确定、必须依赖外部反馈才能继续的任务。优点是适应环境变化、能够动态纠错；缺点是多轮串行调用带来延迟和成本，并且如果没有全局计划与 Runtime 约束，容易绕路、重复调用工具甚至陷入循环。

### Plan-and-Solve：先形成全局计划，再逐步执行

Plan-and-Solve 将“想怎么做”和“真正去做”显式拆开：先针对完整任务生成 Plan，把复杂问题拆成多个子步骤，再按照计划逐项 Solve。

> **Task → Plan → Step 1 → Step 2 → ... → Result**

它的价值是结构清晰、全局性更强，适合逻辑路径较稳定、可以预先拆解的复杂任务。相对 ReAct，它不容易被某一步局部 Observation 带偏；但如果初始计划错误，或者执行途中环境发生变化，静态计划也可能失效，因此生产系统常会进一步加入“失败后重新规划”的机制。

### Reflection：完成一版后，再评审并迭代改进

Reflection 关注的不是第一次如何完成任务，而是**如何对已有结果进行事后自我校正**。Agent 先产生初稿或执行轨迹，再由同一个模型或独立 Reviewer 进行 Critique，找出事实、逻辑、遗漏、效率等问题，随后依据反馈 Refinement；这个过程可以循环，直到质量满足条件或达到迭代上限。

> **Execute → Reflect / Critique → Refine → Reflect → ... → Stop**

Reflection 因此更像一种可以包在其他 Agent Loop 外面的“质量优化层”：第一次执行本身可以采用 ReAct，也可以采用 Plan-and-Solve。它通常以更多模型调用、Token 和延迟换取更高的结果质量，适合代码、报告、复杂推理等质量优先于实时性的任务。

简化来看：**ReAct 解决“下一步根据环境做什么”，Plan-and-Solve 解决“整件事按什么步骤做”，Reflection 解决“做完以后怎样发现问题并改好”。** 实际 Agent 往往把三者组合使用，而不是三选一。

## ReAct 执行循环为什么需要运行时约束？

生产环境中的 ReAct 不应实现为让模型无限“思考 → 调用工具 → 观察 → 再思考”的循环，而应由 Runtime 将其约束为有限状态的执行循环。

1. **设置退出条件**：最大执行轮数、整体超时、Token / 成本预算、连续失败次数和无进展检测，避免死循环。
2. **控制工具执行**：模型只能建议调用什么工具；真正执行前必须经过 Runtime 的工具白名单、参数校验、权限与风险检查。具有副作用的操作还要考虑用户确认和幂等，避免重试造成重复执行。
3. **治理 Observation**：工具结果不应完整追加到上下文，而应结构化、截断和摘要，只保留下一步决策所需信息，避免多轮 ReAct 导致上下文和成本快速膨胀。
4. **维护结构化状态**：不将模型自然语言形式的完整 Thought 作为核心状态，而使用结构化 Tool Call 和 Agent State，记录任务状态、Action、Observation 和 Stop Reason。
5. **支持恢复与追踪**：每一步支持 Checkpoint 和 Tracing，便于工具失败或服务异常后恢复，并定位问题出现在哪次模型或工具调用。
6. **允许非执行出口**：Agent 应能主动结束、向用户澄清、请求确认或转人工，而不是假定所有问题都应通过继续 ReAct 解决。

> **模型负责决定下一步做什么；Runtime 负责限制它能做什么、执行多久、失败后怎么办，以及何时必须停止。**
