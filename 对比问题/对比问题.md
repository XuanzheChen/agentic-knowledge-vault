## CoT、ToT 与 Agent Thought 有什么区别，哪些发生在 LLM 调用内部？

### 原始疑问

调用 LLM API 时，它本身具备 CoT 和 ToT 吗？换言之，API 返回的是一个直接预测器，还是已经集成 CoT / ToT 的预测器？

为什么 Harness 工具有时能看到 API 的“思维链”？这是 LLM 自身的思考，还是 Agentic Loop 产生的 Agent Thought？

### 参考回答（已本地化）

#### CoT（Chain of Thought，思维链）

CoT 是一种**线性推理方式**：模型接到问题后，不直接生成最终答案，而是先经历一系列中间推理，再据此得出结论。

对现代推理模型而言，这种能力可以是模型及其推理系统的一部分。调用 API 时，模型可以自动进行推理，不一定需要 Agent 在外部实现 CoT。

> **CoT 可以发生在单次 LLM 调用内部。**

商业模型通常不会公开完整的内部思维链，而可能只返回最终答案、推理摘要或经过处理的 reasoning 信息。

#### ToT（Tree of Thought，思维树）

ToT 将推理从**一条线**扩展成**一棵搜索树**：模型会针对同一问题产生多个候选思路，对不同分支进行生成、评估、筛选、扩展与回溯，最终选择更优的推理路径。

经典 ToT 本质上是一个**搜索 / 推理框架**，通常需要外部程序多次调用 LLM 并维护搜索树，例如：

- Python 工作流
- Agent Framework
- Harness

LLM 则负责生成、分析或评价树中的节点。

> **CoT 可以发生在一次模型推理内部；经典 ToT 通常是围绕 LLM 构建的外部搜索过程。**

#### Agent 的 Thought

Agent 的 Thought 与模型内部 CoT **不是同一个概念**。典型的 Agentic Loop 为：

> **Thought → Action → Observation → Thought → …**

- **Thought**：根据当前状态决定下一步做什么。
- **Action**：调用工具、执行代码、搜索信息等。
- **Observation**：获取工具执行结果，并将其加入后续上下文。

因此，Agent Thought 更准确地说是**工作流中的显式决策或规划信息**，用于推进工具调用和任务；它与单次模型调用中可能存在的隐藏 reasoning 并不处于同一层。

## KV Cache 与 Prompt Cache 有什么区别？

### 原始疑问

KV Cache 是什么？它如何影响模型部署？与 Prompt Cache 有什么区别？

### 参考回答（已本地化）

> **KV Cache**：避免一次推理过程中重复计算历史 Token。  
> **Prompt Cache**：避免不同 API 请求之间重复计算相同的 Prompt 前缀。

| 对比项 | KV Cache | Prompt Cache |
| --- | --- | --- |
| 缓存内容 | Attention 的 **K、V 张量** | Prompt 前缀对应的可复用推理状态或计算结果；具体实现取决于服务商 |
| 所在层级 | 模型推理层 | Serving / API 基础设施层 |
| 主要目的 | 加速**当前请求**的逐 Token 生成 | 加速并降低**后续请求**中相同前缀的成本 |
| 生命周期 | 通常随当前生成序列存在 | 可跨请求存在一段时间 |
| 用户感知 | 通常完全无感 | API 可能报告 `cached_tokens` 并提供缓存价格 |
| 相同 Prompt 再请求 | 不一定复用上一次的 KV Cache | 可能命中 Prompt Cache |
| 显存影响 | 明显 | 取决于服务端具体实现 |
| 长上下文影响 | 极其重要 | 极其重要，但原因不同 |

## 微调、RAG 与规则增强分别适合解决什么问题？

先判断问题属于知识问题、规则问题，还是模型能力与行为问题。

- **缺少外部知识**：如企业内部文档、实时产品信息或经常更新的数据，优先使用 RAG。知识更新频繁且通常需要可追溯，不适合固化到模型参数中。
- **确定性业务逻辑**：如权限、金额阈值、安全和合规约束，优先放进规则或工作流，因为这些场景要求确定性。
- **稳定的能力或行为缺陷**：模型已经获得正确知识和上下文，但仍反复出现能力或行为问题，例如固定领域的信息抽取长期漏字段、Agent 工具选择与参数生成持续不稳定，或专业表达和输出模式难以通过 Prompt 约束；任务稳定且拥有足够高质量输入输出数据或执行轨迹时，才考虑监督微调或后训练。

训练前还要权衡数据量、任务稳定性、收益与成本。需求变化很快，或 Prompt、RAG、规则已经取得良好效果时，没有必要为训练而训练。

> **缺知识用 RAG，硬约束用规则，稳定且反复出现的模型能力或行为问题才考虑训练。训练是错误归因后解决模型瓶颈的手段，而不是项目效果不好时的默认方案。**

## SFT 与 Full Fine-tuning、LoRA、QLoRA 是什么关系？

它们属于**不同维度**：

- **SFT** 是训练范式 / 训练目标，规定模型利用 Input → Target Response 的监督数据学习期望行为。
- **Full Fine-tuning、LoRA、QLoRA** 是参数更新与训练实现方式，决定训练时哪些参数被更新、需要多少显存和存储成本。

| 概念 | 核心含义 |
| --- | --- |
| **SFT** | 用 Demonstration 和监督损失训练目标行为 |
| **Full Fine-tuning** | 更新模型全部或绝大多数参数 |
| **LoRA** | 冻结基础模型，训练少量低秩 Adapter 参数 |
| **QLoRA** | 量化并冻结基础模型，同时训练 LoRA Adapter |

因此一次 SFT 可以采用 **Full-parameter SFT、LoRA SFT 或 QLoRA SFT**。反过来，LoRA / QLoRA 也可以服务于其他后训练目标，并不是 SFT 的子类型。

> **SFT 回答“模型通过什么训练信号学习”；Full Fine-tuning / LoRA / QLoRA 回答“这些训练信号通过更新哪些参数落到模型上”。**

## Agent 做补全或修 Bug，与 FIM 的差别在哪儿？

对于 IDE 中明确光标位置的代码补全，Serving 层可以直接把光标前后的代码转换成 FIM 所需的 Prefix / Suffix 和控制 Token，再让模型生成 Middle；这些特殊标记通常由系统构造，用户不需要直接看到。

而 **Agent 修 Bug 是更高层的任务执行问题**。Agent 需要理解需求、定位问题、读取相关文件和依赖、决定修改位置与方案，并在修改后运行测试或其他验证。具体代码修改可以通过 FIM、Diff Generation、Edit Tool 或整段重写等方式完成。

因此，FIM 解决的是 **“已知左右上下文，中间应填什么”**；Agent 修 Bug 还要解决 **“哪里需要改、为什么改、怎么改，以及改完是否正确”**。FIM 可以成为 Agent 执行局部编辑时的一种底层能力，但两者不是同一层级。
